# Forge v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Собрать v1 системы Forge — набор Claude Code skills + шаблонов, который проводит проект от анкеты до автономно построенного MVP (спека: `docs/specs/2026-07-29-forge-design.md`).

**Architecture:** Ядро = markdown-артефакты: 4 скилла (`forge-new`, `forge-build`, `forge-status`, `forge-deploy`), читающие шаблоны и конфиг из репо через профиль пользователя (`~/.claude/forge/profile.md`). Вся истина о стройке — в state-файлах репо проекта (state-first). Никакого кода, кроме `install.sh` и его теста.

**Tech Stack:** Claude Code skills (SKILL.md), bash (install), git, gh CLI, telegram-плагин Claude Code.

## Global Constraints

- Ядро без персональных данных владельца (принцип «ядро ≠ профиль», спека §5.7); всё личное — только в `~/.claude/forge/profile.md`.
- Секреты никогда не попадают в git: анкета хранит имена переменных, значения — в `.env` проекта (спека §6).
- Модели по ролям (дефолт, спека §9): анкета/брейншторм/спека/синтез research — `fable`; research-поиск — `sonnet`; диспетчер — `opus`; блок-агент — `opus`; исполнитель — `sonnet`.
- Лимит converge-итераций: `3` (дефолт).
- Язык демо генерируемых продуктов — всегда английский; язык документов Forge — русский.
- Документы для людей (README, спеки) — человеческая проза без имён скиллов и tool-жаргона; служебные файлы (планы, state) — можно.
- Каждая фаза — отдельный скилл; шаблоны отделены от логики (правятся без правки скиллов).
- Имена скиллов v1: `/forge-new`, `/forge-build`, `/forge-status`, `/forge-deploy` (плоские; упаковка в плагин с неймспейсом `forge:` — вне скоупа v1, зафиксировать в беклоге).

- [ ] **Step 3: Написать `install.sh`** — идемпотентный: симлинки `skills/forge-*` → `~/.claude/skills/`; `mkdir -p ~/.claude/forge`; если профиля нет — копия `profile.example.md` с подстановкой `__FORGE_HOME__` на абсолютный путь репо (`sed`); существующий профиль не трогать; вывод — что сделано/пропущено.

```bash
#!/usr/bin/env bash
set -euo pipefail
FORGE_HOME="$(cd "$(dirname "$0")" && pwd)"
SKILLS_DIR="${HOME}/.claude/skills"
PROFILE_DIR="${HOME}/.claude/forge"
mkdir -p "$SKILLS_DIR" "$PROFILE_DIR"
for skill in "$FORGE_HOME"/skills/forge-*/; do
  name="$(basename "$skill")"
  ln -sfn "$skill" "$SKILLS_DIR/$name"
  echo "skill: $name -> linked"
done
if [[ ! -f "$PROFILE_DIR/profile.md" ]]; then
  sed "s|__FORGE_HOME__|$FORGE_HOME|" "$FORGE_HOME/profile.example.md" > "$PROFILE_DIR/profile.md"
  echo "profile: created"
else
  echo "profile: exists, skipped"
fi
```

- [ ] **Step 4: Написать `test/install.test.sh`** — прогоняет install.sh дважды, проверяет: симлинки существуют и указывают в репо; профиль создан, содержит реальный `forge_home` (не плейсхолдер); второй запуск не перезаписал профиль (сравнение mtime/маркер).

```bash
#!/usr/bin/env bash
set -euo pipefail
FORGE_HOME="$(cd "$(dirname "$0")/.." && pwd)"
"$FORGE_HOME/install.sh" > /dev/null
[[ -f "$HOME/.claude/forge/profile.md" ]] || { echo "FAIL: no profile"; exit 1; }
grep -q "forge_home: $FORGE_HOME" "$HOME/.claude/forge/profile.md" || { echo "FAIL: forge_home not substituted"; exit 1; }
echo "custom-marker" >> "$HOME/.claude/forge/profile.md"
"$FORGE_HOME/install.sh" > /dev/null
grep -q "custom-marker" "$HOME/.claude/forge/profile.md" || { echo "FAIL: profile overwritten"; exit 1; }
for s in "$FORGE_HOME"/skills/forge-*/; do
  name="$(basename "$s")"
  [[ "$(readlink "$HOME/.claude/skills/$name")" == "$s" ]] || { echo "FAIL: symlink $name"; exit 1; }
done
echo "PASS"
```

### Task 8: Скилл forge-build (Ф5–Ф7) — диспетчер

**Files:**
- Create: `skills/forge-build/SKILL.md`

**Interfaces:**
- Consumes: всё из T1–T7.
- Produces: команда `/forge-build` в репо Forge-проекта: автономная стройка до MVP на тестовой площадке; одна и та же команда = старт И восстановление (никакого отдельного «resume»).

- [ ] **Step 1: Написать SKILL.md** — цикл диспетчера дословно по спеке §9–10:
  - **Старт = восстановление**: прочитать state-файлы; никаких предположений сверх них; если есть `in_progress`-задачи без живого агента — вернуть в `todo`.
  - **Запуск блоков**: для каждого блока с закрытыми зависимостями — фоновый агент (модель `block_agent`) в worktree `../<repo>-<блок>` (ветка `feat/<блок>`); промпт агенту: его `blocks/<имя>.md` + constitution + ссылки на state; предписанные суб-скиллы: test-driven-development, systematic-debugging, verification-before-completion; внутри блока мелкие задачи — субагентам (модель `executor`); сдача = обновлённые state-файлы + зелёные тесты блока + смоук блока.
  - **Приёмка блока**: ревью диффа → merge worktree → полный прогон тестов проекта → сквозной смоук главного сценария из spec.md → docs-check (blocks/progress/CHANGELOG обновлены, иначе вернуть блок агенту) → `security-reviewer` если блок трогал auth/ввод/БД → запуск следующих по графу.
  - **Вопросы**: новая развилка → `Qnnn` в questions.md + Telegram по протоколу (T5); блокировать только зависимые задачи; ответ владельца → применить, разблокировать; «решай сам» → решение в decisions.md с `кто: auto`.
