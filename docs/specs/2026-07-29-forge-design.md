# Forge — дизайн системы автономной разработки

> Статус: дизайн согласован 2026-07-29, ожидает внешнего ревью. Реализация не начата.
> Hand-maintained. Канонический дом документа: репозиторий `forge`, `docs/specs/`.

## 1. Обзор

**Forge** — личная система spec-driven-разработки поверх Claude Code. Владелец приходит с идеей продукта; система собирает максимально полный «анамнез» (анкета + автоматический research), проводит короткий брейншторм по развилкам, фиксирует детальную документацию (спека, план, блоки) и после одного жёсткого «ок» владельца **автономно строит MVP**: разбивает на блоки, пишет код с тестами, интегрирует, сверяет со спекой циклами и запускает результат на собственной инфраструктуре. Владелец участвует асинхронно через Telegram; простой моделей в ожидании ответов минимизируется.

**Проблема, которую решает:** сегодня каждый новый проект стартует вручную — research, спека, декомпозиция, контроль исполнения требуют постоянного присутствия у терминала, а доступы и инфраструктурные вопросы всплывают в конце, когда они блокируют раскатку.

**Прототип идеологии:** [github/spec-kit](https://github.com/github/spec-kit) (Spec-Driven Development: constitution → specify → plan → tasks → implement → converge). Forge берёт у spec-kit структуру фаз и артефактов, но реализуется как собственный набор Claude Code skills — с тремя надстройками, которых в spec-kit нет: research-фаза, модельная иерархия (Fable/Opus/Sonnet) и неблокирующий автономный цикл стройки.

**Кто использует:** система проектируется **переиспользуемой**: любой пользователь клонирует репо, устанавливает скиллы и работает со своим профилем (свои площадки, свой Telegram-бот, свои дефолты моделей). В ядре — ноль персональных данных владельца; всё личное живёт в профиле пользователя (см. §12). Совместная работа нескольких человек над **одним** Forge-проектом — вне скоупа первой версии, но принцип state-first (вся истина в git-файлах проекта) оставляет это дешёвым расширением: второй участник — это свой Telegram-пейринг и та же очередь `questions.md`, а не переделка архитектуры.

## 2. Поверхности

| Поверхность | Что это | Когда используется |
|---|---|---|
| `/forge:new "идея"` | Скилл: анкета → research → брейншторм → спека/план | Старт проекта, владелец у экрана |
| `/forge:build` | Скилл: автономная стройка **и** восстановление после сбоя (одна команда) | После «ок» по спеке; после падения сессии / rate limit |
| `/forge:status` | Скилл: сводка по tasks/progress/questions | В любой момент |
| `/forge:deploy` | Скилл: раскатка на целевую площадку | После согласования MVP владельцем |
| Telegram-бот | Двусторонний канал: вопросы, отчёты, алерты ↔ ответы владельца | Вся автономная фаза |
| Файлы `docs/forge/` + `tasks.md`, `progress.md` в репо проекта | Источник истины и интерфейс восстановления | Постоянно |

## 3. Сквозной сценарий (primary journey)

1. Владелец: `/forge:new "умная база знаний с сайтом, поиском и TG-ботом"`.
2. **Ф1 Анкета** — интерактивно, у экрана: продукт, поверхности, функционал, референсы, инфраструктура/доступы, ограничения. Доступы валидируются на месте (смоук каждого). «Не знаю» — валидный ответ.
3. **Ф2 Авто-research** — владелец свободен: параллельные агенты копают GitHub (готовые решения/скелеты), рынок (конкуренты, паттерны), стек (доки, версии) → `research-report.md`.
4. **Ф3 Брейншторм** (Fable) — сжатый: только развилки, вскрытые research'ем, и места «не знаю» из анкеты.
5. **Ф4 Спека + план** — constitution, spec, техплан, блоки с графом зависимостей и контрактами.
6. **✅ Гейт** — владелец утверждает пакет документации. Единственная жёсткая остановка.
7. **Ф5 Стройка** — диспетчер запускает блок-агентов в git worktrees; блочные чекпоинты неблокирующие: вопросы уходят в Telegram, работа по независимым задачам продолжается.
8. **Ф6 Converge** — приёмщик со свежим контекстом сверяет продукт со спекой → gap-задачи → цикл (лимит 3 итерации).
9. **Ф7 Запуск** — на тестовой площадке из профиля (у владельца — MUSPELHEIM, fallback — Mac), демо-сид (EN), смоук; в Telegram — ссылка (Tailscale), демо-учётка, отчёт о расхождениях.
10. Владелец щупает MVP с телефона → правки → когда согласовано: `/forge:deploy` на целевую площадку из анкеты.

## 4. Глоссарий

| Термин | Значение |
|---|---|
| **Анкета (intake)** | Канонический шаблонный опрос на старте; самый проработанный артефакт системы |
| **Анамнез** | Разговорное имя Ф1+Ф2: анкета + авто-research |
| **Блок** | Логическая единица продукта (сайт, бот, поиск…) со своей спекой, контрактом и worktree |
| **Диспетчер** | Оркестрирующая сессия автономной фазы: граф задач, запуск блок-агентов, интеграция |
| **Converge** | Итеративная сверка построенного со спекой (термин из spec-kit) |
| **State-first** | Принцип: вся истина в файлах проекта; контекст сессии — расходник |
| **Гейт** | Точка, где система останавливается и ждёт «ок» владельца |
| **MUSPELHEIM** | Домашний Windows-сервер владельца (Tailscale, Docker) — тестовая площадка по умолчанию |

## 5. Принципы

1. **State-first.** Всё, что знает диспетчер, немедленно записывается в файлы. Любая свежая сессия продолжает стройку из файлов, не перечитывая кодовую базу и не строя догадок. Документация — механизм выживания, не побочный продукт.
2. **Docs = Definition of Done** (глобальное правило владельца №4). Ни один агент не сдаёт задачу без обновления `blocks/*.md`, `progress.md`, `decisions.md`, CHANGELOG. Ошибка в доке правится сразу под новые вводные.
3. **Неблокирующие чекпоинты.** Вопрос владельцу блокирует только зависимые от ответа задачи. Цель системы — минимум простоя моделей.
4. **Гибкость на будущее.** Система рассчитана на то, что её будут менять: фазы — отдельные скиллы; шаблоны отделены от логики; конфиг в одном месте; проекты не привязаны к системе (артефакты самодостаточны, lock-in отсутствует). Петля обратной связи: после каждого прогона — ретро → issue в беклог Forge.
5. **Research до реализации** (правило №1 владельца): готовые решения ищутся до написания своего — и на уровне системы (Ф2), и внутри блоков.
6. **Интеллект дорогих моделей — только там, где принимаются решения.** Механика — на дешёвых.
7. **Ядро ≠ профиль.** Скиллы и шаблоны не содержат ничего персонального (серверов, ботов, ников, площадок). Всё личное — в профиле пользователя, который создаётся при установке. Это делает систему переиспользуемой любым человеком без правки ядра.

## 6. Фаза 1: Анкета

Канонический шаблон `templates/intake.md`, результат — `docs/forge/intake.md` в репо проекта.

**Секции:**

| # | Секция | Содержание |
|---|---|---|
| A | Продукт | Цель, проблема, аудитория, главные сценарии, критерии успеха MVP, что точно НЕ делаем |
| B | Поверхности | Web / TG-бот / API / CLI, платформы, язык интерфейса (демо всегда EN — правило №6) |
| C | Функционал | Фичи с приоритетами must / nice |
| D | Референсы | Примеры, конкуренты, «хочу как тут» / «так не хочу» |
| E | Инфраструктура и доступы | GitHub (репо/орг), целевой хостинг, БД, домены, сторонние API, платёжки, аналитика; какие ключи/переменные существуют |
| F | Ограничения | Сроки, предпочтения по стеку, бюджеты на внешние сервисы |

**Правила:**
- Анкета **ветвится** по типу проекта; нерелевантные секции пропускаются. Полнота покрытия, а не длина.
- «Не знаю / решай сам» — валидный ответ → уходит в research или в дефолт.
- Нет доступов к целевой площадке → дефолт: тестовая площадка из профиля пользователя (у владельца — MUSPELHEIM); в беклог автоматически падает задача «выяснить доступы до деплоя».
- **Секреты не в git.** Анкета фиксирует имена и адреса («переменная `DATABASE_URL`, значение в `.env`»); значения — сразу в `.env` (gitignored).
- **Доступы валидируются на месте:** смоук каждого (`gh auth status`, пинг БД, `ssh muspelheim`, тестовый вызов API) → ✅/❌ в анкете.

## 7. Фаза 2: Авто-research

Без владельца. Параллельные Sonnet-агенты, синтез — Fable → `docs/forge/research-report.md` (со ссылками):

- **GitHub**: готовые решения, скелеты, библиотеки (`gh search repos/code`); что взять, что адаптировать, почему своё.
- **Рынок**: конкуренты, аналоги, паттерны UX.
- **Стек**: доки библиотек (Context7 / first-party), версии, совместимость.

Отчёт заканчивается списком **развилок для брейншторма** («есть готовый X — берём или пишем своё?»).

## 8. Фазы 3–4: Брейншторм и документация

- **Брейншторм** — Fable, поверх research-отчёта, развилки по одной. Всё, что закрыто анкетой, повторно не обсуждается.
- **Артефакты Ф4** (шаблоны — по мотивам spec-kit):

```
docs/forge/
├── constitution.md      # принципы проекта; в ходе стройки не меняются
├── intake.md            # анкета (Ф1)
├── research-report.md   # research (Ф2)
├── spec.md              # ЧТО: требования, user stories, DoD MVP
├── plan.md              # КАК: стек, архитектура, решения + почему
├── blocks/<имя>.md      # по блоку: спека, API-контракт, зависимости, статус
├── decisions.md         # ADR-лайт: решения по ходу стройки
└── questions.md         # очередь вопросов владельцу + принятые ответы
tasks.md                 # граф задач со статусами — истина диспетчера
progress.md              # журнал: сделано / в работе / упало
CHANGELOG.md
```

- Всё в git, коммит на каждый значимый шаг. GitHub-репо проекта заводится сразу; задачи зеркалятся в Issues, коммиты закрывают их (`Closes #N`) — правило №3.
- **Гейт**: владелец утверждает пакет (spec + plan + блоки). Дальше — автономия.

## 9. Фаза 5: Автономная стройка

**Модельная иерархия** (дефолты системы; переопределяются в профиле пользователя):

| Роль | Модель | Обоснование |
|---|---|---|
| Анкета, брейншторм, спека, синтез research | Fable | Максимум интеллекта в решениях, определяющих всё дальнейшее |
| Research-поиск | Sonnet | Механический сбор |
| Диспетчер | Opus | Граф, интеграция, конфликты; Fable здесь жёг бы лимиты непропорционально |
| Блок-агенты | Opus | Ведут блок целиком, сами дробят работу |
| Исполнители внутри блока | Sonnet | Код по готовому контракту, тесты, boilerplate |

**Цикл диспетчера** (долгоживущая локальная сессия; гибрид state-first + живой оркестратор):

1. Читает `tasks.md` + `blocks/` → блоки с закрытыми зависимостями готовы к запуску.
2. Запускает блок-агентов **фоном, каждый в своём git worktree** (изоляция — правило №5).
3. Блок готов → ревью результата → merge → интеграционные тесты → обновление файлов состояния → запуск следующих по графу.
4. Вопрос владельцу → `questions.md` + Telegram; блокируются только зависимые задачи.
5. Всё упёрлось в ответы → диспетчер делает «всегда-полезное»: доки, покрытие, демо-сид, converge-проверки.

**Живучесть:** падение сессии / сжатие контекста / rate limit некритичны — `/forge:build` в новой сессии читает `tasks.md` + `progress.md` + `questions.md` и продолжает с точного места. При rate limit — пауза с автопродолжением и уведомлением в Telegram.

## 10. Качество

**Внутри блока:** TDD (superpowers:test-driven-development; красный → зелёный → рефактор); type-check/линт после каждой правки (PostToolUse-хуки); смоук своего флоу перед сдачей; `security-reviewer` на чувствительных местах (auth, ввод, БД), `silent-failure-hunter` перед сдачей.

**На интеграции (диспетчер):** полный прогон тестов проекта — блок не принят, пока не зелёный; сквозной смоук главного сценария спеки; docs-check (блок возвращается агенту, если доки не обновлены).

**Converge (Ф6):** отдельный агент со свежим контекстом читает спеку и щупает продукт как приёмщик → расхождения → gap-задачи → цикл. Лимит **3 итерации** (дефолт системы, переопределяется профилем), затем честный отчёт о несошедшемся.

**DoD MVP (Ф7):** тесты зелёные; продукт запущен на тестовой площадке из профиля (у владельца — MUSPELHEIM, fallback — Mac); демо-режим с сид-данными на английском (правило №6); смоук пройден фактически; converge-отчёт написан. Облачный деплой в DoD **не входит** — это `/forge:deploy` после согласования MVP владельцем.

## 11. Канал Telegram

Официальный telegram-плагин Claude Code (установлен, v0.0.6; канал пока не настроен).

**Настройка (одноразовая, на машину):** `bun` (на нём работает сервер канала; на машине владельца пока не установлен) → бот у @BotFather → `/telegram:configure <токен>` (токен в `~/.claude/channels/telegram/.env`) → пейринг (`/telegram:access pair <код>`) → запереть в `allowlist` (только владелец).

**Ловушка, выясненная по исходникам плагина:** инструменты отправки существуют только в сессии, запущенной с флагом канала (`claude --channels plugin:telegram@claude-plugins-official`). Настроенный канал ≠ доступный канал: без флага токен есть, а отправлять нечем. Поэтому сессия стройки обязана предупреждать в терминал, если инструмента отправки в ней нет, — иначе владелец считает, что уведомления идут, а система молча стоит с вопросом. Отправка по своей инициативе (не в ответ на сообщение) возможна: инструмент `reply` проверяет только, что `chat_id` в списке разрешённых, а сам `chat_id` берётся из `access.json`.

**Протокол сообщений** (шаблоны — в `templates/`):

| Тип | Когда | Формат |
|---|---|---|
| ❓ Вопрос | Развилка, требующая владельца | Контекст 2–3 строки + варианты «1 / 2 / свой ответ»; группируются пачками |
| ✅ Блок готов | Завершение блока | 3–5 строк: сделано, смоук, что стартовало следом |
| ⚠️ Алерт | Застряла / rate limit / среда сломалась | Что случилось + что делает сама / чего ждёт |
| 🏁 MVP готов | Финиш Ф7 | Ссылка (Tailscale), демо-учётка, converge-отчёт, известные расхождения |

Ответы — свободным текстом; «решай сам» валиден (решение → `decisions.md` с пометкой «принято автономно»). Без ответа — не спамит, вопрос ждёт. **Fallback:** Telegram — только транспорт; истина в `questions.md`.

## 12. Упаковка и эволюция

- **Репозиторий `GarroV/forge`** — дом системы: скиллы, `templates/`, `config.md`, доки, ретро. Беклог — Issues этого репо.
- **Структура:**

```
forge/
├── skills/
│   ├── forge-new/SKILL.md        # Ф1–Ф4 (анкета → research → брейншторм → спека)
│   ├── forge-build/SKILL.md      # Ф5–Ф7 (стройка + восстановление)
│   ├── forge-status/SKILL.md
│   └── forge-deploy/SKILL.md
├── templates/                    # анкета, spec, plan, block, протокол Telegram…
├── config.defaults.md            # дефолты системы: модели по ролям, лимит converge…
└── docs/specs/                   # этот документ и последующие
```

- **Профиль пользователя** — `~/.claude/forge/profile.md`, создаётся при установке, в репо системы не попадает: тестовая площадка (у владельца — MUSPELHEIM), целевые площадки, Telegram-канал, переопределения моделей/лимитов. Скиллы читают: профиль → дефолты.
- **Установка (любой пользователь):** клонировать репо → симлинк/копия `skills/` → `~/.claude/skills/forge/` → создать профиль → настроить своего Telegram-бота. У владельца — строчка в bootstrap dotfiles, новые машины получают Forge автоматически.
- **Эволюция:** правки шаблонов не ломают начатые проекты (их артефакты самодостаточны). После каждого прогона — ретро → issue.

## 13. Риски и открытые вопросы

| Риск | Смягчение |
|---|---|
| Лимиты подписки: многочасовая стройка упрётся в rate limit | Пауза + автопродолжение (state-first делает её дешёвой); модельная иерархия; алерт владельцу |
| Mac уснул / закрыт во время стройки | Алерт при старте стройки («не закрывай»); state-first — потеря только времени, не состояния. Перенос диспетчера на MUSPELHEIM — возможная эволюция, в MVP не входит |
| Брейншторм-качество: спека упустила важное → MVP мимо | Converge ловит расхождения со спекой, но не с невысказанными хотелками; лечится правками после MVP — принятый компромисс |
| Слияние worktree блоков конфликтует | Контракты блоков в Ф4 + интеграционные тесты; конфликт решает диспетчер, при сомнении — вопрос владельцу |
| Telegram-плагин: поведение при доставке ответа в долгоживущую сессию под нагрузкой | Проверить фактически на этапе имплементации (принцип №2 владельца); fallback — questions.md |
| MUSPELHEIM недоступен | Явный fallback: запуск на Mac; алерт владельцу |

**Открытые вопросы (решаются при имплементации, не блокируют дизайн):** порядок первого прогона (пилотный проект для обкатки).
