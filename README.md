# Forge

Forge — система разработки поверх Claude Code. На входе — одна фраза об идее
продукта. Система подробно расспрашивает владельца по анкете, сама изучает, как
похожее уже сделали другие, обсуждает только настоящие развилки, пишет спеку, план
и разбивку на части — и после одного «ок» строит MVP сама. Пока она строит,
владелец не нужен: вопросы уходят в Telegram, если поднят канал, а всё, что от
них не зависит, продолжает строиться в любом случае.

Назначение — убрать из начала проекта ручную рутину (расспрос, поиск готовых
решений, декомпозицию, надзор за исполнением) и не обнаружить в конце, что не
хватает доступа к базе или домену.

Идеология — по мотивам [github/spec-kit](https://github.com/github/spec-kit),
реализация своя: набор команд для Claude Code, набор шаблонов и служба
уведомлений. Сам процесс написан текстом, а не программой: код — это установщик,
тесты и мини-сервер канала.

**Первое знакомство или переданный репозиторий** — начать стоит с
[docs/OVERVIEW.md](docs/OVERVIEW.md): что за система, какую задачу решает, чем
отличается от spec-kit, что в ней проверено и что нет. README ниже — про то, как
ей пользоваться.

## На чём она стоит

- **Вся истина о проекте — в файлах проекта.** Задачи, вопросы, решения и журнал
  событий лежат в его репозитории. Поэтому упавшая сессия, кончившийся лимит
  запросов или закрытый ноутбук стоят только времени: следующий запуск читает
  файлы и продолжает с того же места, а не начинает заново.
- **Вопрос владельцу стопорит только то, что от него зависит.** Остальное
  строится дальше. «Решай сам» — валидный ответ; принятое без владельца решение
  записывается и попадает в сводку, даже если сам вопрос забылся.
- **Документы обновляются вместе с кодом**, иначе часть не считается сделанной.
- **Личное живёт в профиле, а не в репозитории.** Площадки, бот, имена машин и
  адрес репозитория системы задаются в `~/.claude/forge/profile.md`; ядро от них
  не зависит. Проверяется тестом чистоты ядра.
- **Язык разговора задаётся профилем** — ключ `language`: на нём система задаёт
  вопросы анкеты, пишет документы проекта, журнал и сводки. Сами шаблоны и
  команды остаются английскими: двух версий одного текста не бывает, они
  расходятся. Демонстрационные данные в построенных продуктах — всегда
  английские, независимо от этого ключа.

## Установка

Нужны: Claude Code и `git`. Плюс авторизованный `gh` (проверяется `gh auth
status`) — без него всё работает, но репозиторий проекта и задачи в Issues
система не создаст и сообщит об этом.

1. Склонировать репозиторий:

   ```
   git clone https://github.com/GarroV/forge.git
   cd forge
   ```

2. Поставить команды:

   ```
   ./install.sh
   ```

   Установщик связывает команды системы и определения её агентов с личным
   каталогом Claude Code и создаёт личный профиль из примера. Запускать повторно
   безопасно: существующий профиль он не перезаписывает.

   Установщик также регистрирует **сторож непрерывности стройки** — хук на
   событие `Stop` в `~/.claude/settings.json`. Чужие настройки он не трогает и
   второй раз себя не добавляет; испорченный `settings.json` не переписывает, а
   сообщает об этом.

   **В уже открытых сессиях новые определения агентов появляются с задержкой.**
   Сразу после установки запуск блока может упасть с `agent type not found` —
   обычно достаточно повторить чуть позже; не помогло — перезапустить Claude
   Code.

   **Сторож непрерывности в уже открытых сессиях не работает вовсе:** харнесс
   снимает хуки снимком при старте сессии. После установки Claude Code нужно
   перезапустить, иначе стройка будет останавливаться после каждого хода, и
   выглядеть это будет как ожидание ответа владельца.

3. Заполнить личный профиль — `~/.claude/forge/profile.md`. В нём: язык разговора
   (`language`, по умолчанию английский), где запускать готовый продукт на
   проверку (эта машина или ssh-хост), включён ли Telegram, лимит сверок со
   спекой. Дефолты, которые профиль перекрывает, лежат в `config.defaults.md` —
   их править не нужно. Значения секретов в профиль не пишутся, только имена и
   адреса.

   Модели задавать не нужно: у агентов системы они заданы в их определениях
   (`agents/`) и применяются сами. Из профиля не задаётся только **модель самой
   сессии**: анкету, спеку и работу диспетчера выполняет она, и переключить её
   изнутри система не может. Команды сообщают, если текущая модель расходится с
   рекомендованной; переключается она через `/model` или `claude --model` при
   запуске.

4. Необязательно, но лучше сразу — канал уведомлений. Общего бота система не
   предоставляет: через него идут внутренности проектов, поэтому бот у каждого
   **свой**. Завести его — минута у @BotFather, дальше `docker compose up -d`,
   адрес и секрет в `~/.claude/forge/channel.env`, в профиле `telegram: on`. В
   самих сессиях включать нечего.

   Проще всего поднять канал **на той же машине, где идёт стройка**: тогда адрес
   — `http://localhost:8090`, и не нужно ни открывать порты, ни настраивать сеть.
   Отдельный сервер нужен ровно для одного — получать вопросы, когда рабочая
   машина выключена; тогда добавляются доступ по сети и проверка снаружи, а не с
   самого хоста. Оба пути — в `channel/README.md`.

   **Плагин Telegram в Claude Code при этом обязан быть выключен**
   (`enabledPlugins` в `~/.claude/settings.json`). Telegram допускает одного
   слушателя на бота: плагин поднимает второго, тот выбивает первого — и выбитый
   не падает, а перестаёт получать сообщения при живом с виду боте. Проверено:
   приём лежал двенадцать минут.

   Что и когда система пишет владельцу — `templates/telegram-protocol.md`. Без
   канала она работает, но вопросы будут ждать в файле, а не в телефоне.

Что сделано и что пропущено, установщик печатает сам. Проверить систему целиком —
прогнать все её тесты, каждый должен сказать `PASS`:

```
for t in test/*.test.sh; do bash "$t"; done
```

Тесты изолированы: профиль и настройки пользователя они не трогают.

Один из них — `test/channel-db.test.sh` — требует интерпретатора с зависимостями
канала и **падает**, если их нет: печатает, чего не хватает, вместо того чтобы
пропустить проверку. Разовая подготовка:

```
python3 -m venv /tmp/forge-channel-venv
/tmp/forge-channel-venv/bin/pip install asyncpg aiohttp aiogram
FORGE_TEST_PYTHON=/tmp/forge-channel-venv/bin/python bash test/channel-db.test.sh
```

## Как вести проект

Команды вызываются словами, в обычном разговоре с Claude Code: отдельного CLI у
системы нет.

Внутри они называются `forge-new`, `forge-build`, `forge-deploy`, `forge-status` —
это глаголы в ряду, как `cargo new` или `rails new`, а не версии системы.
`forge-new` означает «новый **проект**»; никакого «старого Forge» не существует.
Печатать эти имена не нужно, они нужны модели при подборе команды и читателю
репозитория.

### Начать проект

Фраза «новый проект» и описание идеи. Дальше по порядку: анкета (единственная
часть, где нужен владелец), автоматическое исследование, короткий брейншторм
только по развилкам, которые исследование вскрыло, и пакет документов: принципы,
спека, план, описание частей, граф задач. В конце — репозиторий на GitHub с
задачами в Issues и остановка: пока владелец не скажет «ок», стройка не начнётся.
Это единственная жёсткая остановка во всей системе.

Анкета — главный артефакт системы. Она начинается с вопроса «что уже есть»
(только идея, готовое ТЗ, работающий продукт с живыми пользователями, наработки
кода, данные для переноса, дизайн, чужой контракт, срок), и от ответа зависит,
какие вопросы будут дальше и какие правила включатся. Доступы она проверяет
командой на месте, а не верит на слово.

### Отдать в стройку

Фраза «начинай стройку». Система раздаёт части продукта агентам — каждому своя
копия репозитория, чтобы не мешали друг другу, — принимает работу только с
зелёными тестами и живой проверкой сценария, задаёт вопросы, не останавливаясь на
них, в конце сверяет построенное со спекой свежим взглядом и запускает продукт на
проверочной площадке из профиля, с демо-данными.

Стройка при этом **держит себя сама**. Ход сессии в Claude Code заканчивается,
как только модель отвечает текстом, — и раньше стройка вставала ровно между
частями: одна принята, следующая не запущена, будить сессию нечем. Теперь на
каждой попытке закончить ход срабатывает сторож: пока в графе есть задача,
которую можно взять, ход не отдаётся владельцу. Он молчит, пока работают агенты
(их завершение и так вернёт сессию к работе), и отпускает стройку сам, если она
несколько ходов не двигается, — чтобы остановка была видна, а не пряталась за
крутящейся вхолостую сессией. Границы у него тесные и намеренные: не больше 12
удержаний в час и не больше 60 на одну стройку, три хода без движения графа задач
— и он отпускает сам. Коммиты движением не считаются, иначе обычная работа в
репозитории обнуляла бы эту защиту. Сломанный сторож ход не запирает: любая его
ошибка — это отпуск (проверено запуском с намеренно сломанным хуком).

Остановить одну стройку: `python3 <путь-к-forge>/hooks/keep-building.py --stop
<путь-к-проекту>`. Выключить механизм совсем, во всех проектах и вместе с
регистрацией: `python3 <путь-к-forge>/hooks/keep-building.py --off`.

Та же фраза продолжает прерванную стройку — отдельной команды «продолжить» нет.
Пока стройка идёт, машину лучше не выключать: она работает на ней.

### Посмотреть, что происходит

Фраза «статус стройки» — задачи по статусам, части в работе, вопросы, ожидающие
ответа, решения, принятые без владельца, последние события и следующий шаг. Эта
команда ничего не меняет и стройку не продолжает, её можно звать в любой момент.

### Раскатать на боевую площадку

Фраза «раскатай» или «выложи на сервер». Готовый MVP до этого остаётся на
проверочной площадке из профиля: сама наружу система ничего не выкладывает.
Раскатка на целевую площадку из анкеты — отдельный шаг и отдельное «да» владельца
в том же разговоре, никогда не по факту зелёных тестов. Доступы к площадке
команда перепроверяет заново, а не верит анкете: пока она заполнялась, токен мог
истечь, а хост — переехать. Результат проверяется снаружи, по внешнему адресу —
успешный ответ изнутри сервера не говорит о том, что продукт открывается у
пользователей.

## Что готово, а что нет

Система собрана не до конца, и это стоит знать до первого запуска. Снимок
состояния — [docs/STATUS.md](docs/STATUS.md): что работает, что нужно от
владельца, какие решения приняты по ходу. Задачи —
в [Issues](https://github.com/GarroV/forge/issues), план реализации —
в [docs/plans/2026-07-29-forge-v1.md](docs/plans/2026-07-29-forge-v1.md).

Коротко: команды выше написаны, покрыты тестами и обкатаны на служебном проекте —
от одной фразы до работающего продукта, без владельца. Канал уведомлений
развёрнут и проверен в обе стороны 07.08.2026: отправка доходит, ответ владельца
забирается. По итогам собственных прогонов система заводит задачи на свои
шероховатости в [Issues](https://github.com/GarroV/forge/issues) — это и есть
точный счёт сделанного и открытого, в README он устаревал бы за день. Не
проверено: анкета на живом человеке (нужно около получаса времени владельца) и
раскатка на настоящую площадку.

## Что где лежит

```
skills/               команды системы, по каталогу на каждую
agents/               роли агентов стройки: блок-агент, исполнитель, поисковик.
                        Модель роли живёт здесь и применяется сама
channel/              бот и мини-сервер уведомлений: разворачивается на той же
                        машине или на отдельном хосте, если вопросы нужны при
                        выключенной рабочей машине
templates/            шаблоны, которые они заполняют:
  intake.md             стартовая анкета — самый проработанный шаблон
  constitution.md       принципы проекта
  spec.md               что строим
  plan.md               как строим
  block.md              описание одной части продукта
  block-agent-brief.md  задание агенту на часть: собирается из шаблона, а не
                          пишется каждый раз заново
  research-report.md    итог исследования, кончается развилками
  retro.md              разбор прогона: что мешало системе
  issue-style.md        как система пишет задачи и комментарии в трекер
  telegram-protocol.md  что и когда система пишет владельцу
  state/                форматы файлов состояния: задачи, вопросы, решения, журнал
hooks/                механизмы, которые работают без участия модели:
  keep-building.py      сторож непрерывности — не отдаёт ход владельцу, пока в
                          графе есть работа, которую можно взять
config.defaults.md    дефолты системы; личное — в профиле, не здесь
install.sh            установщик
test/                 тесты системы и заполненные примеры-фикстуры
docs/                 дизайн системы, план реализации, статус, исследования
```

Шаблоны отделены от команд: чтобы изменить формулировку вопроса в анкете или
состав спеки, трогать команды не нужно. Начатые проекты от правки шаблонов не
ломаются — их документы самодостаточны и от системы не зависят.

Дизайн системы целиком, с обоснованием решений:
[docs/specs/2026-07-29-forge-design.md](docs/specs/2026-07-29-forge-design.md).
