# Канал: бот и мини-сервер уведомлений

Часть Forge, а не отдельный проект: живёт в этом репозитории, задачи — в этом же
беклоге. Разворачивается на домашнем сервере как `C:\projects\forge-channel`.

## Зачем он нужен

Стройка идёт без владельца и должна уметь две вещи: **сообщать** («часть готова»,
«нужно решение», «встали», «готово») и **получать ответ**. До этого канал жил
плагином внутри сессии Claude Code, и это упиралось в устройство Telegram:

**Telegram допускает одного слушателя на токен.** Два одновременных опроса дают
`409 Conflict`, причём вылетает *первый*, а второй продолжает работать. Выбитая
сессия не падает — она молча перестаёт получать сообщения, бот при этом выглядит
живым. То есть каждая новая сессия отбирала канал у предыдущей, и стройка ждала
ответа, который до неё уже не мог дойти. Проверено экспериментом, не выведено из
документации.

Здесь ботом владеет **один постоянный процесс** на сервере. Сессии с ним говорят
по HTTP: сколько бы их ни было, конфликтовать нечему. Флаг запуска сессии больше
не нужен.

## Как устроено

```
любая сессия Claude Code ──HTTP (Tailscale)──►  канал на MUSPELHEIM  ──►  Telegram ──► владелец
            ▲                                    │        ▲
            └────────── GET /inbox ──────────────┘        └── ответ владельца (long polling)
```

Два контейнера, по конвенции сервера (`muspelheim-infra/_template`): свой Postgres
с меткой бэкапа и бот. Бот держит в одном процессе опрос Telegram и HTTP-интерфейс.

| Файл | Что это |
|---|---|
| `bot/core.py` | чистая логика: доступ, разбор запроса, нарезка длинного текста. **Без внешних зависимостей** — проверяется на любой машине без Docker |
| `bot/db.py` | две таблицы: журнал отправленного и очередь ответов |
| `bot/main.py` | точка входа: опрос Telegram + HTTP-интерфейс |
| `docker-compose.yml` | Postgres (метка `backup.pgdump=true`) + бот |
| `keep-port-open.ps1` | лечение блокировки порта Docker Desktop — без него канал выглядит мёртвым с Mac |
| `.env.example` | имена переменных; рабочий `.env` не коммитится |

## Интерфейс

Все вызовы, кроме проверки живости, требуют `Authorization: Bearer <FORGE_SECRET>`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/notify` | `{"project":"…","kind":"question\|block\|alert\|done","text":"…"}` → отправляет владельцу, пишет в журнал |
| `GET` | `/inbox` | неразобранные ответы владельца: `{"pending":[{"id","text","received_at"}]}` |
| `POST` | `/ack` | `{"ids":[1,2]}` — пометить разобранными |
| `GET` | `/healthz` | `{"status":"ok","polling":true}`; `503`, если база не отвечает |

Два решения, которые стоит понимать:

- **Формулировки сообщений придумывает система, не канал.** Канал добавляет только
  шапку со значком и именем проекта. Иначе протокол сообщений оказался бы описан в
  двух местах и разъехался.
- **Ответы помечаются разобранными отдельным вызовом,** а не самим чтением. Падение
  между «прочитал» и «применил» иначе съедало бы ответ владельца молча.

## Развёртывание

Требуется: доступ к серверу и заполненные секреты. Порт `8090`; занято на сервере
`5678` (n8n), зарезервировано за погашенным стендом `8020/8043/5433/6543`.

```powershell
# 1. Положить код на сервер как C:\projects\forge-channel
#    (папка = имя compose-проекта, поэтому контейнеры не пересекутся с чужими)

# 2. Заполнить секреты
cd C:\projects\forge-channel
Copy-Item .env.example .env
notepad .env    # BOT_TOKEN, FORGE_SECRET, OWNER_CHAT_ID, POSTGRES_PASSWORD

# 3. Поднять
docker compose up -d --build
docker compose ps
docker compose logs -f bot

# 4. Держать порт открытым снаружи (иначе с Mac канал недоступен)
schtasks /Create /TN "Forge channel keep port open" /SC MINUTE /MO 10 /RU SYSTEM `
  /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\projects\forge-channel\keep-port-open.ps1"
schtasks /Run /TN "Forge channel keep port open"
```

## Как проверить, что живой

С Mac, по адресу сервера в Tailscale:

```bash
# 1. Живость — без секрета
curl -s http://<сервер>:8090/healthz          # ожидание: {"status":"ok","polling":true}

# 2. Отправка — сообщение должно прийти в Telegram
curl -s -X POST http://<сервер>:8090/notify \
  -H "Authorization: Bearer $FORGE_SECRET" -H 'content-type: application/json' \
  -d '{"project":"forge","kind":"block","text":"проверка канала"}'

# 3. Приём — ответить боту в Telegram, затем
curl -s http://<сервер>:8090/inbox -H "Authorization: Bearer $FORGE_SECRET"
```

**Проверка «отвечает локально на сервере» ничего не доказывает:** loopback идёт мимо
inbound-фильтра, и порт может быть закрыт именно снаружи. Проверять только с Mac.

## Чего здесь сознательно нет

- **Вебхука.** Он потребовал бы публичного HTTPS-адреса, а сервер за Tailscale.
  Опрос из одного постоянного процесса решает ту же задачу без выставления наружу.
- **Чужой инфраструктуры.** Паттерн «облачная функция + вебхук» у владельца обкатан
  в другом проекте, и соблазн занять её был. Нельзя: инструментом строят в том
  числе тот продукт, и если канал ломается от чужого деплоя, Forge нельзя
  использовать ровно тогда, когда он нужен.
- **Общего бота с продуктами.** Через канал идут внутренности проектов: спеки,
  решения, имена переменных. У ботов продуктов другая аудитория.

## Как прошло развёртывание (07.08.2026) — факт, а не замысел

Развёрнуто на домашнем сервере, проверено **с Mac**. Порядок оказался ровно таким,
как описан выше, с двумя уточнениями, которые стоит знать заранее.

**Код доставлен копированием, а не клоном.** Репозиторий системы приватный, и клон
на сервере потребовал бы держать там доступ к GitHub. Копия по SSH этого не требует:
`scp -r ./channel/. <сервер>:"C:/projects/forge-channel/"`. Обратная сторона — копия
на сервере не подтягивает обновления сама; после правок в репозитории её надо
перекопировать.

**`.env` доставлен файлом, а не командой.** Секреты, переданные в строке команды,
видны в списке процессов сервера. Собираются локально во временный файл с правами
`600`, копируются, локальный удаляется.

**Секрет для вызовов с Mac живёт в личном профиле,** не в репозитории:
`~/.claude/forge/channel.env` (права `600`) — там же адрес канала. Это то же
правило, что для токена бота: личное — в профиле.

### Ложное «работает», на которое стоит не попасться

Порт с Mac ответил **до** установки задачи удержания. Причина: блокировка, которую
вешает Docker Desktop, — **машинная, а не по портам**, и задача другого проекта на
этом сервере снимает её глобально. То есть канал в тот момент работал за счёт
чужого проекта: погаси тот проект — и после следующего рестарта Docker канал молча
отвалился бы с Mac при живых контейнерах.

Поэтому у канала своя задача (каждые 10 минут + при старте) и своё правило
разрешения, а скрипт снимает блок Docker сам, а не надеется на соседа. Проверять
надо не «отвечает ли порт», а «отвечает ли он благодаря нашей задаче».

### Что проверено фактически

| Проверка | Результат |
|---|---|
| `GET /healthz` с Mac | `{"status":"ok","polling":true}` |
| `POST /notify` без секрета и с неверным секретом | `401` |
| `POST /notify` с негодным `kind` | `400` с перечислением допустимых |
| `POST /notify` рабочий | сообщение доставлено владельцу в Telegram |
| Ответ владельца → `GET /inbox` | ответ забран |
| `POST /ack`, затем повторный `ack` тех же | `acked: 1`, затем `acked: 0` без ошибки |

Оба контейнера `restart: unless-stopped`, у Postgres метка `backup.pgdump=true` —
очередь ответов попадает в ежедневный дамп сервера.

### Известное, не починенное

В логах бота `DeprecationWarning`: состояние приложения меняется после его старта
(`app["polling_ok"]` в `main.py`). Работает, но на будущих версиях aiohttp сломается
— вынести флаг в отдельный объект состояния.
