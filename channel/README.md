# Канал: бот и мини-сервер уведомлений

Часть Forge, а не отдельный проект: живёт в этом репозитории, задачи — в этом же
беклоге. Разворачивается двумя контейнерами там, где тебе удобно: проще всего — на
той же машине, где идёт стройка.

## Зачем он нужен

Стройка идёт без владельца и должна уметь две вещи: **сообщать** («часть готова»,
«нужно решение», «встали», «готово») и **получать ответ**. До этого канал жил
плагином внутри сессии Claude Code, и это упиралось в устройство Telegram:

**Telegram допускает одного слушателя на токен.** Два одновременных опроса дают
`409 Conflict`, причём вылетает *первый*, а второй продолжает работать. Выбитая
сессия не падает — она молча перестаёт получать сообщения, бот при этом выглядит
живым. То есть каждая новая сессия отбирала канал у предыдущей, и стройка ждала
ответа, который до неё уже не мог дойти. Проверено экспериментом, не выведено из
документации.

Здесь ботом владеет **один постоянный процесс** на сервере. Сессии с ним говорят
по HTTP: сколько бы их ни было, конфликтовать нечему. Флаг запуска сессии больше
не нужен. **Но плагин Telegram в Claude Code обязан быть выключен** (`enabledPlugins`
в `~/.claude/settings.json`): он поднимает второго слушателя того же бота и выбивает
канал. Коварно то, что он включается настройкой, а не флагом, — то есть стартует в
каждой сессии сам, и перезапуск сессии не помогает. Проверено: приём канала лежал
двенадцать минут, пока плагин работал.

## Как устроено

```
любая сессия Claude Code ──────HTTP──────►  канал (твой хост)  ──►  Telegram ──► владелец
            ▲                                    │        ▲
            └────────── GET /inbox ──────────────┘        └── ответ владельца (long polling)
```

Два контейнера: свой Postgres (очередь ответов и журнал отправленного) и бот. Бот
держит в одном процессе опрос Telegram и HTTP-интерфейс.

| Файл | Что это |
|---|---|
| `bot/core.py` | чистая логика: доступ, разбор запроса, нарезка длинного текста. **Без внешних зависимостей** — проверяется на любой машине без Docker |
| `bot/db.py` | две таблицы: журнал отправленного и очередь ответов; адресация ответов по реплаю |
| `bot/main.py` | точка входа: опрос Telegram + HTTP-интерфейс |
| `docker-compose.yml` | Postgres + бот; метка `backup.pgdump=true` — зацепка для внешнего бэкап-скрипта, если он у тебя есть |
| `keep-port-open.ps1` | **нужен только на Windows** и только если канал стоит на другом хосте: Docker Desktop вешает inbound-BLOCK на свой backend, и порт перестаёт отвечать снаружи. При запуске на своей машине не нужен вовсе |
| `.env.example` | имена переменных; рабочий `.env` не коммитится |

## Интерфейс

Все вызовы, кроме проверки живости, требуют `Authorization: Bearer <FORGE_SECRET>`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/notify` | `{"project":"…","kind":"question\|block\|alert\|done","text":"…"}` → отправляет владельцу, пишет в журнал |
| `GET` | `/inbox` | `?project=<имя>` — неразобранные ответы, адресованные этому проекту (и безадресные): `{"pending":[{"id","text","project","received_at"}]}`. Без параметра отдаётся всё |
| `POST` | `/ack` | `{"ids":[1,2],"project":"…"}` — пометить разобранными. Чужие id не помечаются и возвращаются в `rejected` со статусом `409` |
| `GET` | `/healthz` | `status`, `polling`, `last_update_fetch_sec_ago`, `conflicts_in_a_row`, `last_error`; `503`, если база не отвечает **или опрос выбит** |

### Кому адресован ответ

Очередь ответов одна на все стройки, а строек может идти несколько. Адрес берётся
из реплая: владелец отвечает реплаем на сообщение канала, канал по id сообщения
находит в журнале отправленного, чей это был вопрос, и помечает ответ этим
проектом. Поэтому в сообщениях, после которых ждут ответа (`question`, `alert`),
канал сам просит ответить реплаем, а в подтверждении приёма называет проект —
или честно пишет, что адресата не понял.

Ответ не реплаем адреса не имеет и виден всем: достаться не тому плохо, но не
достаться никому — хуже.

Два решения, которые стоит понимать:

- **Формулировки сообщений придумывает система, не канал.** Канал добавляет только
  шапку со значком и именем проекта. Иначе протокол сообщений оказался бы описан в
  двух местах и разъехался.
- **Ответы помечаются разобранными отдельным вызовом,** а не самим чтением. Падение
  между «прочитал» и «применил» иначе съедало бы ответ владельца молча.

## Развёртывание

Нужны: свой бот у @BotFather и Docker. Каталог, в котором лежит канал, задаёт имя
compose-проекта — держи его отдельным, чтобы контейнеры не пересекались с чужими.

```bash
# 1. Заполнить секреты
cp .env.example .env
$EDITOR .env        # BOT_TOKEN, FORGE_SECRET, OWNER_CHAT_ID, POSTGRES_PASSWORD

# 2. Поднять
docker compose up -d --build
docker compose ps
docker compose logs -f bot
```

Дальше — адрес и секрет в личный профиль (`~/.claude/forge/channel.env`:
`CHANNEL_URL`, `FORGE_SECRET`, права `600`) и `telegram: on` в профиле системы.

**Проще всего — на той же машине, где идёт стройка:** тогда
`CHANNEL_URL=http://localhost:8090`, и ни портов наружу, ни настройки сети не
нужно. Честный минус: спящая машина уведомлений не получает — ответы копятся в
Telegram (около суток) и подхватываются при пробуждении; стройка в это время тоже
стоит, так что рассинхронизации нет.

**Отдельный хост** нужен ровно для одного — получать вопросы, когда рабочая машина
выключена. Тогда добавляется два шага: открыть порт снаружи и проверить канал **с
рабочей машины**, а не с самого хоста. На Windows с Docker Desktop понадобится ещё
`keep-port-open.ps1` задачей планировщика: Docker вешает inbound-BLOCK на свой
backend, порт перестаёт отвечать с других хостов, а локально при этом отвечает —
это и путает диагностику.

## Как проверить, что живой

Проверять **не с того хоста, где стоит канал** (при локальном запуске это одно и
то же — тогда просто с этой машины):

```bash
# 1. Живость — без секрета
curl -s http://<адрес>:8090/healthz          # ожидание: {"status":"ok","polling":true}

# 2. Отправка — сообщение должно прийти в Telegram
curl -s -X POST http://<адрес>:8090/notify \
  -H "Authorization: Bearer $FORGE_SECRET" -H 'content-type: application/json' \
  -d '{"project":"forge","kind":"block","text":"проверка канала"}'

# 3. Приём — ответить боту в Telegram РЕПЛАЕМ на сообщение из шага 2, затем
curl -s "http://<адрес>:8090/inbox?project=forge" -H "Authorization: Bearer $FORGE_SECRET"
#    ожидание: ответ на месте, поле "project" равно "forge"

# 4. Адресация — чужой проект этот ответ видеть не должен
curl -s "http://<адрес>:8090/inbox?project=someone-else" -H "Authorization: Bearer $FORGE_SECRET"
#    ожидание: {"pending":[]}
```

**Если канал на отдельном хосте, ответ «работает локально на нём» ничего не
доказывает:** loopback идёт мимо inbound-фильтра, и порт может быть закрыт именно
снаружи.

## Чего здесь сознательно нет

- **Вебхука.** Он потребовал бы публичного HTTPS-адреса, а хост может стоять в частной сети.
  Опрос из одного постоянного процесса решает ту же задачу без выставления наружу.
- **Чужой инфраструктуры.** Паттерн «облачная функция + вебхук» у владельца обкатан
  в другом проекте, и соблазн занять её был. Нельзя: инструментом строят в том
  числе тот продукт, и если канал ломается от чужого деплоя, Forge нельзя
  использовать ровно тогда, когда он нужен.
- **Общего бота с продуктами.** Через канал идут внутренности проектов: спеки,
  решения, имена переменных. У ботов продуктов другая аудитория.

## Как прошло развёртывание (07.08.2026) — факт, а не замысел

Развёрнуто на домашнем сервере, проверено **с рабочей машины**. Порядок оказался ровно таким,
как описан выше, с двумя уточнениями, которые стоит знать заранее.

**Код доставлен копированием, а не клоном.** Репозиторий системы приватный, и клон
на сервере потребовал бы держать там доступ к GitHub. Копия по SSH этого не требует:
`scp -r ./channel/. <сервер>:"C:/projects/forge-channel/"`. Обратная сторона — копия
на сервере не подтягивает обновления сама; после правок в репозитории её надо
перекопировать.

**`.env` доставлен файлом, а не командой.** Секреты, переданные в строке команды,
видны в списке процессов сервера. Собираются локально во временный файл с правами
`600`, копируются, локальный удаляется.

**Секрет для вызовов с рабочей машины живёт в личном профиле,** не в репозитории:
`~/.claude/forge/channel.env` (права `600`) — там же адрес канала. Это то же
правило, что для токена бота: личное — в профиле.

### Ложное «работает», на которое стоит не попасться

Порт снаружи ответил **до** установки задачи удержания. Причина: блокировка, которую
вешает Docker Desktop, — **машинная, а не по портам**, и задача другого проекта на
этом сервере снимает её глобально. То есть канал в тот момент работал за счёт
чужого проекта: погаси тот проект — и после следующего рестарта Docker канал молча
отвалился бы с рабочей машины при живых контейнерах.

Поэтому у канала своя задача (каждые 10 минут + при старте) и своё правило
разрешения, а скрипт снимает блок Docker сам, а не надеется на соседа. Проверять
надо не «отвечает ли порт», а «отвечает ли он благодаря нашей задаче».

### Что проверено фактически

| Проверка | Результат |
|---|---|
| `GET /healthz` с рабочей машины | `{"status":"ok","polling":true}` |
| `POST /notify` без секрета и с неверным секретом | `401` |
| `POST /notify` с негодным `kind` | `400` с перечислением допустимых |
| `POST /notify` рабочий | сообщение доставлено владельцу в Telegram |
| Ответ владельца → `GET /inbox` | ответ забран |
| `POST /ack`, затем повторный `ack` тех же | `acked: 1`, затем `acked: 0` без ошибки |

Адресация ответов (26.08.2026) проверена тестами на настоящем Postgres —
`bash test/channel-db.test.sh` из корня репозитория: реплай приносит проект,
чужой `/inbox` его не видит, чужой `ack` получает `409` и ответ остаётся ждать,
а база со старой схемой мигрирует, не теряя ответов.

**И проверена на живом канале в день раскатки**, а не только тестами:

| Проверка на живом канале | Результат |
|---|---|
| Обновление контейнера на базе с данными | схема получила колонку `project`, все 19 записей журнала и очереди на месте |
| Ответ владельца реплаем на вопрос проекта `forge` | в очереди с `project: forge` — адрес определился сам |
| `GET /inbox?project=` с чужим именем | ответы другого проекта не видны |
| `POST /ack` с чужим именем на чужой id | `409`, ответ остался ждать адресата |
| `GET /inbox?project=-bad-name` | `400` с причиной |
| `POST /ack` с телом `{"ids":"1,2"}` | `400` |
| `GET /inbox` без секрета | `401` |
| Хвост сообщений `question` | в журнале отправленного стоит просьба ответить реплаем |
| Старые ответы без адреса | видны всем, как задумано — ничего не потерялось |

Оба контейнера `restart: unless-stopped`, у Postgres метка `backup.pgdump=true` —
очередь ответов попадает в ежедневный дамп сервера.

### Починено 07.08.2026 по живому сбою

Плагин Telegram в сессии выбил канал, и **проверка живости этого не показала**: она
отдавала `ok`, потому что флаг «опрашиваю» ставился один раз при старте. Приём лежал
двенадцать минут при зелёном `healthz`.

Заменено: вместо `dp.start_polling` — свой цикл опроса, отмечающий **каждую** удачную
выборку. `healthz` показывает, когда она была, сколько конфликтов подряд и текст
последней ошибки, и отдаёт `503`, когда опрос мёртв. Канал **сам пишет владельцу**,
что его выбили: отправка при конфликте работает. Заодно ушёл `DeprecationWarning` —
состояние переехало из объекта приложения в отдельный держатель.

Проверено провокацией настоящего конфликта: во время него `503` и
`conflicts_in_a_row: 3`, после прекращения — `200` и запись «опрос восстановлен».
