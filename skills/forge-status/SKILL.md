# forge-status

Сводка по текущему ходу автономной стройки Forge-проекта: сколько задач в каком
статусе, какие блоки сейчас в работе, какие вопросы ждут владельца, какие
решения система приняла сама, и что логично сделать дальше. Источник истины —
markdown-файлы состояния в репозитории проекта (state-first): их и нужно
прочитать и осмыслить, а не гадать по кодовой базе.

## Важно: только чтение

Этот скилл **read-only**. Он не пишет и не редактирует ни один файл проекта, не
делает `git commit`/`git push`, не запускает блок-агентов и не продолжает стройку.
Единственное действие — прочитать файлы состояния (инструментами чтения файлов и
директорий) и вывести сводку в чате. Если по ходу возникает соблазн что-то
«поправить» или доделать — не делай этого, это не задача этой команды.

## Шаг 1 — это Forge-проект?

Посмотри содержимое текущей рабочей директории. Признак Forge-проекта — наличие
подкаталога `docs/forge/`.

Если `docs/forge/` не существует — это не Forge-проект. Выведи ровно одно
сообщение:

```
Это не Forge-проект: в текущей директории нет docs/forge/.
```

и остановись. Не пытайся читать `tasks.md`, `progress.md` или что-либо ещё —
если `docs/forge/` нет, дальше нечего парсить.

## Шаг 2 — конфиг (необязателен, ни на что не блокирует)

Это лёгкое обогащение сводки, а не предпосылка для неё — если что-то из этого шага
не найдётся, просто пропускай соответствующую часть и переходи к шагу 3.

1. Проверь `~/.claude/forge/profile.md`.
   - Файл есть → прочитай его YAML-шапку, возьми значение `forge_home`.
   - Файла нет → выведи один раз строку `Профиль Forge не найден — работаю на
     дефолтах системы.` и воспользуйся фолбэком вместо `forge_home`: каталог
     этого скилла лежит внутри репозитория системы по пути
     `<forge_home>/skills/forge-status/`, значит `config.defaults.md` находится
     ровно на два уровня выше **каталога скилла** (не выше самого файла
     SKILL.md). Каталог скилла обычно известен из контекста его запуска
     (например, строка «Base directory for this skill: ...», которую сообщает
     харнесс при загрузке скилла): если он равен `.../skills/forge-status`, то
     искать нужно `.../config.defaults.md`. Если и так найти не удалось —
     просто продолжай без значений из шага 2, они опциональны.
2. Если путь к `config.defaults.md` известен (из `forge_home` или из фолбэка
   выше) и файл существует — прочитай его YAML-шапку. Тебе нужны только
   `converge_limit` и `telegram`.
3. Если те же ключи (`converge_limit`, `telegram`) заданы и в шапке самого
   `profile.md` — они переопределяют значения из `config.defaults.md` (профиль
   всегда главнее дефолтов).

Результат шага 2 — это просто два опциональных значения (`converge_limit`,
`telegram`), которые пригодятся в шаге 8. Ничего страшного, если они останутся
неизвестны.

## Шаг 3 — прочитать файлы состояния проекта

Раскладка (см. `docs/forge/` — она уже подтверждена наличием на шаге 1):

- `tasks.md` — в корне проекта.
- `progress.md` — в корне проекта.
- `docs/forge/questions.md` — вопросы владельцу.
- `docs/forge/decisions.md` — решения по ходу стройки.

Попробуй прочитать все четыре. Если `docs/forge/` есть, а какого-то из этих
файлов нет — не пытайся угадывать его содержимое. Вместо этого в финальной
сводке (шаг 10) замени соответствующий блок ровно одной строкой «файл
`<имя>` отсутствует» и продолжай с тем, что есть; остальные блоки строй
нормально. Конкретно, какой файл — на какой блок влияет:

- `tasks.md` отсутствует → блоки «Задачи» и «Активные блоки» (шаги 4–5)
  заменяются **одной общей** строкой «файл `tasks.md` отсутствует» (не по строке
  на каждый из двух блоков); «Следующий шаг» (шаг 9) в этом случае тоже
  фиксированный — см. правило в начале шага 9.
- `progress.md` отсутствует → блок «Последние события журнала» (шаг 8)
  заменяется строкой «файл `progress.md` отсутствует»; строку про попытки
  сверки со спекой в этом случае просто не показывай.
- `questions.md` отсутствует → блок «Открытые вопросы владельцу» (шаг 6)
  заменяется строкой «файл `questions.md` отсутствует»; в шаге 9 правило про
  открытый вопрос считается несработавшим (нет данных — значит, для целей
  «следующего шага» открытого вопроса не нашлось).
- `decisions.md` отсутствует → блок «Решения, принятые без тебя» (шаг 7)
  заменяется строкой «файл `decisions.md` отсутствует».

При разборе таблиц (`tasks.md`, `questions.md`, `decisions.md`) игнорируй:
- строку-разделитель `|---|---|...|`;
- закомментированные строки-примеры внутри `<!-- ... -->` (это шаблонная
  подсказка, а не реальные данные — грамматически они всё равно начинаются с
  `<!--`, а не с `|`).

Учитывай только строки вида `| Tnnn | ... |` (для `tasks.md`), `| Qnnn | ... |`
(для `questions.md`) или `| Dnnn | ... |` (для `decisions.md`).

## Шаг 4 — задачи по статусам

Если `tasks.md` отсутствует — пропусти подсчёт, но не сам раздел: в сводке его
место занимает строка про отсутствующий файл (см. шаг 3). Молча пропадать
раздел не должен.

Пройди по строкам `tasks.md` и посчитай задачи по каждому статусу из контракта:
`todo`, `in_progress`, `done`, `failed`, `blocked:Qnnn` (все `blocked:Qnnn`
считаются одной категорией «blocked» — конкретный номер вопроса не важен для
счётчика, он важен для раздела вопросов ниже). Посчитай также общее число задач.

## Шаг 5 — активные блоки

Если `tasks.md` отсутствует — пропусти подсчёт, но не сам раздел: в сводке его
место занимает строка про отсутствующий файл (см. шаг 3). Молча пропадать
раздел не должен.

«Активный блок» — это блок (значение колонки «блок» в `tasks.md`), в котором
**хотя бы одна** задача сейчас в статусе `in_progress`, `blocked:Qnnn` или
`failed` — то есть блок либо в работе прямо сейчас, либо стоит и требует
внимания. Блок, где все задачи только `todo` (ещё не начат) или только `done`
(уже закончен), в активные не входит.

Для каждого активного блока перечисли, какие именно задачи держат его активным
(id + статус), чтобы было понятно, что происходит, а не только что «что-то
происходит».

## Шаг 6 — открытые вопросы владельцу, полным текстом

Если `questions.md` отсутствует — пропусти разбор, но не сам раздел: в сводке
его место занимает строка про отсутствующий файл (см. шаг 3).

Возьми из `questions.md` все строки со статусом `open`. Для каждой выведи id,
**полный текст** колонки «вопрос» (не сокращай и не пересказывай) и что она
блокирует (колонка «блокирует» — id задач, или «—», если ничего явно не
указано).

Если открытых вопросов нет (есть только `answered`/`auto` или таблица пуста) —
одна строка: «Открытых вопросов нет.»

## Шаг 7 — решения, принятые без тебя

Если `decisions.md` отсутствует — пропусти разбор, но не сам раздел: в сводке
его место занимает строка про отсутствующий файл (см. шаг 3).

Владелец периодически отходит от компьютера, пока система строит автономно; то,
что она успела решить сама без него — первое, что он хочет увидеть, вернувшись.

Возьми из `decisions.md` строки, где колонка «кто» равна `auto` (строки с
`owner` сюда не идут — это решения самого владельца, ему не нужно рассказывать
о них как о новости). Из отобранных `auto`-строк возьми **последние 3** в
порядке следования файла (`decisions.md` — как и остальные state-файлы,
пополняется по ходу стройки, поэтому последние строки — самые свежие решения).
Для каждой коротко выведи id, «решение» и «почему» (сокращать формулировки не
нужно — они уже короткие по контракту, но и пересказывать в 3 раза длиннее
тоже не нужно).

Если `auto`-строк нет вовсе — одна строка: «Автономных решений не было.»

## Шаг 8 — последние события журнала

Если `progress.md` отсутствует — пропусти разбор, но не сам раздел: в сводке его
место занимает строка про отсутствующий файл (см. шаг 3).

Возьми строки данных `progress.md` (пропуская HTML-комментарии и заголовок) и
выведи последние **5** — если их меньше пяти, выведи все, какие есть. Строки
показывай как есть, целиком (формат `YYYY-MM-DD HH:MM [роль] событие` — это уже
готовый человеческий текст, его не нужно ни парсить дальше, ни сокращать).

Отдельно посчитай, сколько строк с ролью `[converge]` (проверки соответствия
спеке) есть **во всём `progress.md`** — по всему файлу целиком, а не только
среди последних 5 показанных строк выше (эти множества могут не совпадать: в
файле может быть больше 5 записей, и старые попытки converge из «последних 5»
выпадут, но в счётчик должны попасть все). Если таких строк больше нуля,
добавь отдельную короткую строку: сколько таких попыток было, и если
`converge_limit` известен из шага 2 — из какого лимита («попыток сверки со
спекой в журнале: 1 из 3»). Если `converge_limit` неизвестен — просто число
попыток без знаменателя. Если попыток сверки не было вовсе (0 строк
`[converge]` во всём файле) — эту строку не показывай.

## Шаг 9 — следующий шаг

Если `tasks.md` отсутствует — следующий шаг фиксирован независимо от всего
остального: «Состояние стройки не найдено, вероятно проект ещё не прошёл фазу
планирования.» Дальше в этом шаге ничего не проверяй.

Иначе определи основную фразу «что дальше» правилами 1–3 по порядку —
побеждает **первое** сработавшее (если `questions.md` отсутствует, правило 1
считается несработавшим — см. шаг 3):

1. **Есть открытый вопрос** (шаг 6 нашёл хотя бы один `open`) → основная фраза
   — дождаться ответа владельца на этот вопрос (назови id). Если при этом есть
   задачи `in_progress`, не зависящие от ответа, упомяни, что работа по ним
   продолжается параллельно (неблокирующий чекпоинт — вопрос стопорит только
   зависимые задачи, а не всю стройку).
2. **Иначе есть задача со статусом `failed`** → основная фраза — разобраться в
   причине сбоя этой задачи (назови id и блок), прежде чем блок может двигаться
   дальше.
3. **Иначе есть задача `in_progress`** → основная фраза — она продолжается
   (назови id и блок), явных решений от владельца сейчас не требуется.

Правило 4 (готовые к старту `todo`-задачи) проверяется **всегда**, независимо
от того, сработало ли уже одно из правил 1–3: найди `todo`-задачи, у которых
**все** id из колонки «зависит от» имеют статус `done` (или колонка пуста/«—»)
— это задачи, готовые к старту прямо сейчас. `Todo`-задачи, у которых в
«зависит от» есть id с любым другим статусом (например, зависимость сама ещё
`todo`/`in_progress`, или что важнее — `failed`), в готовые не включай: их
зависимость не выполнена, стартовать им рано.

- Если ни одно из правил 1–3 не сработало и такая готовая задача нашлась — она
  сама становится основной фразой: «эта задача готова к старту: <id> (<блок>)».
- Если одно из правил 1–3 уже сработало и при этом нашлась независимая готовая
  задача — добавь отдельным предложением к основной фразе: «независимо от
  этого доступна для старта задача <id> (<блок>) — её зависимости уже
  выполнены».

Если готовых к старту задач нашлось несколько — назови **первую по порядку
строк в `tasks.md`**, а про остальные добавь только счёт: «и ещё N готовых к
старту». Перебирать все не нужно, а выбор «какую назвать» не должен зависеть от
настроения: одно и то же состояние файлов обязано давать одну и ту же сводку.

Правило 5 (fallback): если не сработало ни одно из правил 1–4 (нет открытого
вопроса, нет `failed`, нет `in_progress`, нет ни одной готовой к старту
`todo`-задачи) → основная фраза: «всё выполнено», если при этом все задачи
`done`; иначе — «доступной для старта работы сейчас нет» (например, все
оставшиеся `todo`-задачи ждут не done зависимостей).

## Шаг 9а — идёт ли стройка на самом деле

Граф задач говорит, что **осталось** сделать, но не говорит, **делается** ли это
сейчас. Владелец спрашивает про статус ровно тогда, когда не уверен, — и разница
между «стройка идёт» и «стройка стоит и ждёт твоего сообщения» для него важнее
любой таблицы.

```bash
python3 <forge_home>/hooks/keep-building.py --status .
```

- Печатает **«непрерывный режим выключен»** → стройка сейчас не идёт сама:
  ближайший ход сессии закончится, и ничего не продолжится, пока владелец не
  напишет. Так и скажи — прямо, одной строкой, вместе с тем, что доступной работы
  осталось столько-то. Не пиши «стройка идёт» на одном основании, что задачи не
  закрыты.
- Печатает JSON маркера → режим включён; полезное оттуда: `released_reason`
  (сторож сам отпустил стройку — значит она несколько ходов не двигалась) и
  `last_hold_at` (когда он в последний раз возвращал сессию к работе).
- Команда не нашлась или упала — так и скажи одной строкой и не гадай: сводка
  без этого пункта остаётся верной, а выдуманный ответ — нет.

Это read-only, как и всё остальное в сводке: `--status` ничего не меняет.
Включать и выключать режим — дело команды стройки, а не сводки.

## Шаг 9б — не отстал ли граф от трекера

Граф — источник правды для стройки, но работа умеет утекать мимо него: находки
заводятся в трекере, задачи берутся оттуда, коммиты ссылаются на номера issue, а
в граф это не возвращается. Сбой тихий и выглядит как успех — сводка показывает
«почти всё сделано», хотя на самом деле диспетчеру нечего раздать.

Если у проекта есть трекер и `gh` доступен, сравни два числа:

```bash
gh issue list --state open --limit 200 --json number | python3 -c 'import json,sys; print(len(json.load(sys.stdin)))'
```

против числа задач графа в статусе не-`done`.

- Числа сопоставимы — всё в порядке, отдельной строки в сводке не нужно.
- **Открытых в трекере кратно больше** — скажи прямо: граф отстал от того, что
  происходит, и стройку в таком состоянии запускать бессмысленно — она возьмёт
  давно сделанную задачу и упрётся. Измерено на живом проекте: 171 `done` в графе
  при 74 открытых задачах в трекере, стройка простояла полтора месяца, и
  обнаружилось это вопросом владельца, а не системой.
- Трекера нет, `gh` не установлен или репозиторий не определяется — скажи одной
  строкой, что сверка не делалась, и не гадай.

Колонка `issue` в `tasks.md` делает сверку точной: по ней видно, какие открытые
задачи трекера уже есть в графе, а какие в него не попали вовсе.

## Шаг 10 — вывести сводку

Собери всё в одну человекочитаемую сводку на языке из настроек (`language`), без служебных терминов
вроде названий скиллов, ролей-исполнителей или внутренних команд (роли из
`progress.md`, показанные как часть исходных строк журнала на шаге 8 — не
трогать, это цитата файла, а не твоя формулировка; статус-коды `done`,
`in_progress`, `todo`, `failed`, `blocked` — тоже не переводить и не менять:
это те же литералы, что в файле, так удобнее сверять глазами). Ориентировочная
форма (не шаблон для копирования один в один, а порядок и состав разделов;
любой блок ниже может быть заменён строкой про отсутствующий файл — см. шаг 3):

```
Статус стройки: <имя каталога проекта>

[строка про профиль, только если он не найден — см. шаг 2]

Задачи (всего N): done — X, in_progress — X, blocked — X, todo — X, failed — X

Активные блоки:
- <блок> — <какие задачи держат его активным>
(или «Активных блоков нет: вся текущая работа либо завершена, либо ещё не начата.»)

Открытые вопросы владельцу:
- <Qnnn>: <вопрос полным текстом> (блокирует: <id задач или «—»>)
(или «Открытых вопросов нет.»)

Решения, принятые без тебя:
- <Dnnn>: <решение> — <почему>
(или «Автономных решений не было.»)

Последние события журнала:
<до 5 строк progress.md как есть>
[строка про попытки сверки со спекой, если применимо — см. шаг 8]

Следующий шаг: <фраза по правилам шага 9>
```
